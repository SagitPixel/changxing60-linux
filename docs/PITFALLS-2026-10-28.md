# 6.18 移植踩坑记录（2026-10-28）：显示 / 刷机 / WiFi

机器：畅行 60（ZTE 7552N / P720S20），UMS9620（qogirn6pro），内核
`6.18.54-7552n-probe1+`，rootfs 为 UFS 上的 OpenWrt 25.12（loop 挂载）。

这份文档只记“看起来像 A、实际是 B”的坑，以及每个坑最后靠什么证据定位。结论先给：

- **显示**：已稳定。DSI 复位、背光 shutdown、5.4 状态页 daemon 三处缺一不可；
  后来的绿线是 6.18 多加的 OCP2131 偏压写，恢复 5.4 时序后消失；重启后灰屏另有一个
  原因：未 strip 的 `sprd-drm.ko` 会 `invalid module format`（见 §3.7）。
- **刷机**：UFS 早就能用，刷机不需要 Android；但 UFS 的 LUN 编号会变，必须按
  `PARTNAME` 找分区，不能硬编码 `/dev/sda40`。
- **WiFi（2026-10-29 更正）**：2.4GHz / 5GHz WPA2 热点均已由用户实测连接并打开后台。
  根因包括 WCN 资源解析提前退出，以及错误地按 AB 芯片版本强选 XPE 配置。
  本机实读 IPD=0，应使用普通 INI。详情以 `WIFI-STATUS-2026-10-29.md` 为准。
- **音频**：扬声器和听筒都可用——AW87xxx 的 `Music`（扬声器）/ `Receiver`（听筒）
  两个 profile；听筒不是 codec EAR（`rcv dvld -110` 是死路）。

## 1. 显示

### 1.1 灰屏不是“Linux 崩溃”造成的

第一次灰屏时 pstore 里是：

```
insmod-fail sprd-drm.ko insmod: can't insert '/linux-modules/sprd-drm.ko': invalid module format
/dev/dri/card0 不存在
changxing60-screen: no /dev/dri/card*: No such file or directory
```

内核、rootfs、USB、SSH 都是活的。随后设备被 `mobile-data` 的 300 秒 last-resort
reboot 带回 Android。**崩溃/看门狗只是把设备带到下一次启动；灰屏本身是显示链路没有
初始化、或没有正常关闭。**

### 1.2 DSI 控制器从来没被复位（第一个真根因）

6.18 的 `qogirn6pro/global_dsi.c` 用 reset framework：

```c
ctx_reset = devm_reset_control_get(&pdev->dev, "dsi_rst");
s_ctx_reset = devm_reset_control_get(&dsi->dev, "s_dsi_rst");
```

但厂商 DTB 是 5.4 风格：

```
dsi@31300000  reset-syscon = <&glbregs 0x04 0x02>;
dsi1@31400000 reset        = <&glbregs 0x04 0x04>;  syscon-names = "reset";
```

节点上没有 `resets`/`reset-names`，`devm_reset_control_get()` 直接失败：

```
[drm][dsi_glb_parse_dt]   read ctx_reset failed
[drm][dsi_s_glb_parse_dt] read s_ctx_reset failed
```

`dsi_reset()` 里 `IS_ERR(ctx_reset)` 为真，于是**从不 assert/deassert**。从 Android
接手时 DSI 还在跑，Linux 再初始化就得到一个灰/残影面板。

修法：在 `qogirn6pro/global_dsi.c` 里保留 reset framework 优先，失败时回退到
`syscon_regmap_lookup_by_phandle_args(np, "reset-syscon"/"reset", 2, args)`，并在
`dsi_reset()/dsi_s_reset()` 里 toggle 对应位。修好后 dmesg 会出现：

```
[drm][dsi_glb_parse_dt]   dsi reset via reset-syscon reg=0x4 mask=0x2
[drm][dsi_s_glb_parse_dt] dsi1 reset via syscon reg=0x4 mask=0x4
```

补丁：`kernel/patches/display-dsi-reset-syscon.patch`。

**教训**：面板灰先看 `dmesg | grep -i "ctx_reset\|dsi reset"`，不要先怀疑背光。

### 1.3 5.4 的 `changxing60-screen` 把背光写成 0%（第二个真根因）

DSI 修好后，面板仍会“灰/黑”，`logread` 里是：

```
changxing60-screen[2829]: changxing60-screen: backlight 0%
changxing60-screen[2829]: changxing60-screen: 3 input device(s)
```

它是 5.4 的自绘状态页 daemon，会接管 DRM 并把背光写成 0%。6.18 上由 fbcon 拥有面板，
这个 daemon 不该跑。

处理（两层）：

- 现场：`/etc/init.d/changxing60-screen stop`，删除
  `/etc/rc.d/S95changxing60-screen`（持久，重启不再启动）；
- 仓库：`openwrt/overlay/etc/init.d/changxing60-screen` 的 `start_service()` 开头加
  `uname -r` 的 `6.*` guard，直接 `return 0`。

**教训**：面板灰/黑时先看 `cat /sys/class/backlight/*/brightness` 和
`logread | grep -i screen`。背光是 0，就是它。

### 1.4 背光 PWM 没有 shutdown，Linux 重启把最后一帧留在面板上

`sprd_drm_shutdown()` 调了 `drm_atomic_helper_shutdown(drm)`，但 backlight 的 PWM 是
独立设备，没有 `.shutdown`：Linux reboot/poweroff 后背光保持最后一次亮度，面板停在最后
一帧。Android 的显示驱动要过一段时间才重新初始化，于是看到灰屏/残影。

修法：`sprd_disp/sprd_bl.c` 给 `sprd_backlight_driver` 加：

```c
static void sprd_backlight_shutdown(struct platform_device *pdev)
{
	struct backlight_device *bd = platform_get_drvdata(pdev);
	if (!bd)
		return;
	bd->props.brightness = 0;
	bd->props.power = FB_BLANK_POWERDOWN;
	bd->props.state |= BL_CORE_FBBLANK;
	backlight_update_status(bd);
}
...
.shutdown = sprd_backlight_shutdown,
```

验证：Linux → Android 正常重启，Android 面板正常（不再灰）。补丁存于
`kernel/patches/display-backlight-shutdown.patch`。

**教训**：只改 DRM shutdown 不够，PWM/背光要单独关；从 Linux 回 Android 走正常
`reboot`/`poweroff`，不要长按电源硬断电。

### 1.5 init 的显示守卫

`boot/init` 在 `mdev -s` / `modules-done` 之后等 `/dev/dri/card0`（最多 20 秒）：

```
stage=display-ok wait=N s
stage=display-missing wait=N s   ← 没有 card0，把背光关掉，再继续
```

没有 DRM 时把背光写 0，至少不会留下一个亮着的灰屏。日志行可用于事后判断。

### 1.6 面板灰了怎么恢复（操作约定）

1. 先回 Android，**放 10–15 分钟**，让 Android 的显示驱动重新初始化背光/DSI
   （本机两次都是这样恢复的，不需要拆机）。
2. 不要连续重启、不要反复进 Linux。
3. 一直不恢复再彻底关机/断电，最后才拆电池冷启动。
4. 显示驱动没修好之前，不要拿面板反复做实验。

### 1.7 绿线：6.18 多写的 OCP2131 偏压寄存器

灰屏修好后，面板在 Linux 下出现**绿线**；回 Android 就正常（Android 会重新初始化面板
偏压）。静态检查面板电源路径后，发现 6.18 比 5.4 多了一段 I2C 写：

5.4（`drivers/gpu/drm/sprd/sprd_dsi_panel.c`，工作正常）：

```c
regulator_enable(panel->supply);
if (avdd_gpio) { gpiod_direction_output(avdd_gpio, 1); mdelay(5); }
if (avee_gpio) { gpiod_direction_output(avee_gpio, 1); mdelay(5); }
if (reset_gpio) { 按 sprd,reset-on-sequence 拉 reset; }
```

6.18（`drivers/unisoc_platform/sprd_disp/sprd_dsi_panel.c`）：

```c
regulator_enable(panel->supply);
if (avdd_gpio) {
    gpiod_direction_output(avdd_gpio, 1);
    mdelay(1);
    OCP2131_write_bytes(0x00, 0x14);   /* 5.4 没有 */
    mdelay(5);
}
if (avee_gpio) {
    gpiod_direction_output(avee_gpio, 1);
    mdelay(1);
    OCP2131_write_bytes(0x01, 0x14);   /* 5.4 没有 */
    mdelay(5);
}
if (reset_gpio) { ... }
```

关键点：

- `ocp2131.ko` 在模块集里，`lcd_bias/ocp2131.c` 的 `OCP2131_write_bytes()` 在 I2C client
  存在时会真的写寄存器；0x00/0x01 是 AVDD/AVEE 偏压寄存器。
- 5.4 的同一块板、同一颗 OCP2131 **从来不写**这两个寄存器；偏压由 LK/Android 设好，
  Linux 只负责把 AVDD/AVEE 的 enable GPIO 拉高。
- 6.18 把 `0x14` 写进去，覆盖了原来的偏压 → 绿线；回 Android 后 Android 重新初始化
  OCP2131，所以又正常。

修法：恢复 5.4 的时序，AVDD/AVEE 只拉 GPIO + `mdelay(5)`，删掉两次 OCP2131 写。
只重编 `sprd-drm.ko`，不动内核 Image。补丁
`kernel/patches/panel-power-ocp2131.patch`；换入后绿线消失，当前 known-good 镜像是
`work/boot-618-wifi-panel-pwr.img`。

**教训**：面板电源不是“能亮就行”。从别的板子移植过来的 I2C 偏压写会覆盖 LK/Android
已经设好的值，典型症状就是绿线/花屏；AVDD/AVEE 的 GPIO + 延时以 5.4 为准，OCP2131
寄存器写要单独确认这块板是否真的需要。

## 2. 刷机与分区

### 2.1 UFS 能用，刷机不需要 Android

rootfs 在 UFS 上，Linux 里可以直接 dd `boot_b` / `misc`。Android 现在只是**面板异常时的
恢复环境**，不参与刷机。

### 2.2 UFS 的 LUN 编号每次启动会变（差点写坏 boot_b）

曾经在 Linux 里硬编码：

```
dd if=image of=/dev/sda40     # boot_b
dd if=bcb  of=/dev/sda3      # misc
```

某次启动后 `/dev/sda` 不是 128 GB 的那块 UFS LUN，写完 `sha256sum /dev/sda40` 与镜像
不一致，BCB 读回是空；设备随后回退 Android。**不要按 `sda/sdb/sdc` 猜**。

正确做法：扫 `/sys/class/block/*/uevent` 的 `PARTNAME`：

```sh
for u in /sys/class/block/*/uevent; do
    [ "$(sed -n 's/^PARTNAME=//p' "$u")" = boot_b ] && echo /dev/$(basename "$(dirname "$u")")
done
```

脚本：`tools/flash-boot-image.sh`（写 boot_b + trial-B BCB）。现在写之前会：校验镜像与 BCB 的
sha256 必须等于调用方给的期望值；BCB 必须是随 ramdisk 出厂的那一条 trial-B（结构 + 整条 sha256）；
misc 的 PARTNAME 必须唯一命中且正好 1 MiB；把整个 misc 备份到 `/root/changxing60-backup/`
并读回校验。写 BCB 时显式 `count=32`，写后除了比对这 32 字节，还把整块 misc 与备份做 diff，
证明 2048..2079 之外一个字节都没动；任何一处不符就自动把备份写回。脚本不再自动 reboot。
支持 `DRY_RUN=1` 只校验不动盘。

### 2.3 BCB 两个 32 字节文件不要混

| 用途 | sha256 | md5 |
|---|---|---|
| trial B（Linux 优先，试两次回 A） | `9e2f7c07…271d48e2` | `77ce02a0bbf8e659fc8e75f33da4d2ad` |
| slot A（强制下次进 Android） | `56290070…7ffc3ebb` | `3cb2fd6f56506d8c0ff0f86e4d71e0ca` |

曾经把 slot A 的文件当 trial B 写进 misc，结果重启进 Android，还误以为“刷机失败”。
写之前确认文件名和内容，写之后 `dd … | md5sum` 对照。

misc 偏移 `0x800` 的这 32 字节是 `bootloader_control`，实测布局（三条已知记录都通过 CRC，
所以 LK 读的就是这个布局）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | `slot_suffix`：`_a\0\0` / `_b\0\0` |
| 4 | 4 | magic，小端 `0x42414342` = `BCAB` |
| 8 | 1 | version = 1 |
| 9 | 1 | nb_slot = 2 |
| 10 | 1 | recovery_tries_remaining |
| 11 | 1 | merge_status |
| 12 | 8 | slot_info[4]，**每槽 2 字节**：bit0-3 priority（15 最高、0 不可启动），bit4-6 tries_remaining，bit7 successful_boot，后跟 1 字节保留（必须 0） |
| 20 | 8 | 保留，必须全 0 |
| 28 | 4 | crc32_le（小端）：对 0..27 字节做 zlib crc32 |

trial B = `_b`、A(14/7/successful)、B(15/2/not-successful)；恢复 A = `_a`、A(15/7/successful)、
B(14/2/not-successful)。`tries_remaining == 1 && !successful` 会被 LK 当成“已失败”，所以试跑
必须写 2。

校验工具：`python tools/bcb.py check <file>`（结构 + magic + 保留字节 + CRC，并打印每个槽的
priority / tries / successful）。

这两条记录的 sha256 还被写进了 `boot/init`（`MISC_BC_A_SHA` / `MISC_BC_B_SHA`）和
`tools/flash-boot-image.sh`（`MISC_BC_B_SHA`）：只允许写“出厂随 ramdisk 的那一条”，
任何手工改动过的记录（哪怕 CRC 重算过）都会被拒绝。**如果确实要换记录，三处要一起改，
并用 `bcb.py check` 确认 CRC 和槽位策略。**

### 2.4 `/tmp` 是 tmpfs，重启就没了

一次 `scp` 了镜像和脚本到 `/tmp`，中间设备重启；再执行
`sh /tmp/flash-boot-image.sh …; sync; reboot` 时脚本已经不存在，`sh` 失败但 `reboot`
照样执行——白重启一次，镜像根本没写。**刷机脚本/镜像放 `/root/` 或每次重新 push；
并且不要用 `; reboot` 串在可能失败的命令后面。**

### 2.5 整个 misc 被写坏的那一次（2026-10-28）

从 Android 里用 `adb push` 推 32 字节 BCB，push 因为 Git Bash 把
`/data/local/tmp/...` 转成了 `C:/Program Files/Git/data/local/tmp/...` 而失败；
后面的命令仍然继续：`su -c 'dd of=/dev/block/by-name/misc bs=1 seek=2048 conv=notrunc'`
**没有 `count`**、没有检查 push 是否成功、没有检查 dd 返回码、读回 md5 没有和期望值比对，
最后无条件 `reboot`。misc 的内容被写坏，设备只能拆机救回。

要写 misc 必须同时满足：

1. **源文件先落盘并校验**：sha256 等于期望值、大小正好 32、结构通过（`tools/bcb.py check`）。
2. **先备份整块 misc 并读回校验**，备份放在非 tmpfs 的位置（`/root/…`）。
3. **显式 `count=32 conv=notrunc`**：写入长度的上限写在命令里，不依赖源文件大小。
4. **每一层都判断返回码**，任何一步失败就停；绝不用 `;` 把写盘和 `reboot` 串起来。
5. **写后证明只有这 32 字节变了**（整块 diff），不符就把备份写回。
6. **不要自动重启**：让人看过读回结果再决定。

### 2.6 整分区备份 ≠ 可以乱写

有整盘备份只意味着“理论上能救回来”，不意味着可以拿 misc 做试验。拆机、短接、重新分区
的成本远高于写之前多花三十秒做校验。上面 2.5 的六条是硬性要求，不是建议。

## 3. 内核与模块

### 3.1 Image 与模块必须同一次构建

旧模块 + 新 Image 的 `sprd-drm.ko` 报 `invalid module format`。模块集与 Image 必须来自
同一次 `build-6.18-probe.sh` + `make modules`；每次换 Image 都要重打模块。

### 3.2 `CONFIG_SDIOHAL` 内置版与 WCN 模块自带的 sdiohal 冲突

6.18 配置原来是 `CONFIG_SDIOHAL=y`，而 `wcn_bsp.ko` 自己又带一套
`sdio/sdiohal_*.o`，于是：

```
WCN SDIO: sdiohal_scan_card
Error: Driver 'sdiohal' is already registered, aborting...
WCN SDIO: wait scan card time out
```

修法：`kernel/build-6.18-probe.sh` 的 fragment 里加 `# CONFIG_SDIOHAL is not set`，
让模块里的那份 sdiohal 接管。

注意：第一次 scan（`WCN_AUTO`）会注册驱动；第二次（`sprd_wlan_combo`）的
“already registered” 是噪声，但**卡不回**要看后面的 `wait scan card time out` 和
`mmc1` 的 CMD5 响应。

### 3.3 SDHCI 电源寄存器：历史判断需更正

2026-10-29 更正：以下当时的单因判断不成立。成功扫描时也读到过 Power=0，不能用它
证明外部 WCN 没上电。当前保留 set_power_noreg 兼容调用，但还需核对实际 regulator/GPIO
资源、SDIO 应答和运行状态；不得照此推断强制电压就能修复。

6.18 的 sdhci 核心：驱动一旦安装 `.set_power`，核心就把写 `SDHCI_POWER_CONTROL` 的活
全部交给 vendor 回调，自己不再写。6.18 移植过来的 `sdhci_sprd_set_power()` 只配
regulator，于是：

```
mmc1: SDHCI Power = 0x00
mmc1: Cmd 0x0502 (CMD5) Argument 0x00000000, Resp 0
```

修法：在 `sdhci_sprd_set_power()` 末尾补：

```c
sdhci_set_power_noreg(host, mode, vdd);
```

这是 WiFi SDIO 能上电的前提。

### 3.4 wifi 槽的 OCR / non-removable

2026-10-29 更正：本节下方是已撤回的假设，禁止继续套用。当前使用原厂 3.0–3.1V OCR，
清除 NONREMOVABLE 以允许 WCN 上电后重扫；已有 BROKEN_CARD_DETECTION 会把 get_cd
视为存在。原厂 Wi-Fi host 没有 vmmc/vqmmc supply，不得猜接 SD 卡槽电源或 1.2V vddwcn。
SDIO 已实际协商 1.8V SDR104 / 208MHz，无须强制信号电压。补丁已更新为实测版本。

`sdio@22220000`（`sprd,name = sdio_wifi`）没有 `vmmc-supply`/`vqmmc-supply`；dummy
regulator 的 OCR mask 可能为 0，`mmc_power_up()` 拿到的 `vdd` 就是 0。已在
`sdhci_sprd_probe()` 里对 `sdio_wifi` 强制 3.3 V OCR，并加 `MMC_CAP_NONREMOVABLE`
（该槽没有 CD GPIO，否则 `mmc_rescan()` 可能直接跳过、不发 CMD5）。

做完这两步后仍然是 `wait scan card time out`。当时据此怀疑 SC2355 的 SDIO I/O 是
1.8 V，需要 host 强制 `SDHCI_CTRL_VDD_180` —— **这个方向已作废**：后来实测 SDIO 自己
协商到 1.8 V SDR104 / 208 MHz，不需要强制信号电压（见 3.4 开头的更正）。
真正的断点不在这里，而在 WCN 模块没进镜像和 INIT 选择上。

以上 `sdhci-sprd` 的三处改动（`sdhci_set_power_noreg`、3.3 V OCR、`MMC_CAP_NONREMOVABLE`）
存于 `kernel/patches/mmc-sdhci-wifi-power.patch`。

### 3.5 镜像 body 上限 56 MiB，WCN 模块要 strip

repack 报：

```
image data (63654144 bytes) overlaps the persistent log area at 56 MiB
```

未 strip 的 `wcn_bsp.ko`（6 MB）+ `sprd_wlan_combo.ko`（21.5 MB）放不进 initramfs。
用 `aarch64-linux-gnu-strip --strip-debug` 后是 757 KB + 2.98 MB；repack 时对这两个
名字跳过（基镜像里已有 stripped 版本）。ramdisk 现在约 24.7 MB，body 约 53 MiB，仍
低于 56 MiB 的 persist log。

### 3.6 rootfs 里的 `/lib/modules/6.18.56` 模块不能用

rootfs 自带一套 6.18.56 的模块（`wcn_bsp`/`sprd_wlan_combo` 等），但内核是
`6.18.54-7552n-probe1+`，加载报：

```
.gnu.linkonce.this_module section size must match the kernel's built struct module size
init_module: Exec format error
```

必须用同一 6.18.54 构建的模块；rootfs 里的 6.18.56 模块只能作为“参考存在”，不要
modprobe。

### 3.7 重启后 `sprd-drm.ko` invalid module format：模块必须 strip

第一次 Linux→Linux 重启又灰屏，pstore 里是：

```
[   12.048057] insmod-fail sprd-drm.ko insmod: can't insert '/linux-modules/sprd-drm.ko': invalid module format
[   12.077602] stage=modules-done loaded=29 failed=3
```

`/dev/dri/card0` 不存在，`display-missing`，面板灰。但**第一次从 Android 启动是正常的，
模块也是同一份镜像**——差别是未 strip 的 `sprd-drm.ko` 有 11,990,208 字节，整个
initramfs 24.7 MB。把 30 个模块全部 `aarch64-linux-gnu-strip --strip-debug` 后：

- `sprd-drm.ko` 11,990,208 → 1,113,096；
- ramdisk 24,708,275 → 11,998,926；
- 连续 3 次 Linux→Linux 重启都是 `display_ok=1`、`fb0=1`、`invalid=0`、背光 69；
- 走 slot-A BCB 进 Android、再用 trial-B BCB 进 Linux（Android→Linux）也一次通过，
  同样 `display_ok=1`、`fb0=1`、`invalid=0`、背光 69。

所以镜像构建的最后一步必须 strip 模块（WCN 那两个之前已经 strip 过），不要为了
“保留调试符号”把 12 MB 的显示模块塞进 initramfs；大模块在重启路径上会以
`invalid module format` 的形式失败，表现就是灰屏。known-good 镜像
`work/boot-618-wifi-panel-pwr-stripped.img`。

### 3.8 不要运行时 rmmod WCN 模块换参数（会 panic，然后消耗 slot B 次数）

为了试 `legacy_fw_compat=0`，在已启动的系统里做了
`rmmod sprd_wlan_combo; rmmod wcn_bsp; insmod … legacy_fw_compat=0`，结果是
`device_link_release_fn` 里 Oops（`Modules linked in: … [last unloaded: wcn_bsp]`），
而 init 里设了 `panic_on_oops=1` / `panic=10`，所以直接变成重启；重启又被当成一次
失败的 slot B 启动，把试跑次数用掉，最后回 Android。

5.4 的结论（`docs/FINDINGS.md` §14）就是 `rmmod wcn_bsp` 会崩内核；6.18 上
`sprd_wlan_combo`（SDIO/combo 的 glue）也属于同一个不允许卸载的分类。**验证参数变体
只有一个办法：重新打包 ramdisk 镜像（参数写在 init 的 insmod 里），不要热插拔模块。**
`wcn_bsp`/`sprd_wlan_combo` 依赖链上的 `device_link` 在卸载时不会按加载顺序反解，
这跟“先 rmmod 上层再 rmmod 下层”没有关系。

### 3.9 `resolve-order.sh` 重新生成的模块列表会少一截

`boot/module-order-618.txt` 在 3849bb2 里从 32 条变成 27 条：加进了 4 个电源模块，
却掉了 `wcn_bsp` / `sprd_wlan_combo`（少了就没 Wi-Fi）、`sprd-sipc-virt-bus` /
`sprd_modem_loader` / `spipe` / `spool` / `sipa-core` / `sipa_eth` / `sipa-dele`
（少了就没 modem 和 SIPA 网络）、`sprd_vpu_pw_domain` / `drm_kms_helper` /
`unisoc-iommu` / `drm_client_lib` / `drm_dma_helper` / `ocp2131` / `sprd-drm`
（少了就灰屏）。共 16 条。

原因是那份列表由 `boot/resolve-order.sh` 用 depmod 闭包生成，而它的 roots 只列了
音频和电源的入口模块。用 `boot/make-618-image.sh` 按这份列表整份重建，做出来的镜像
没有无线、没有内屏。**增量路径不受影响**：`tools/build-power-on-baseline.py` 是从
已验证镜像的 `etc/module-order` 出发，只往前面加电源模块，所以线上那个镜像是好的。

已修：`boot/module-order-618.txt` 按线上镜像里的那份恢复成 43 条，`resolve-order.sh`
的 roots 补上了 wcn / sipa+modem / drm 三组。`boot/init` 里之前只在
`build-power-on-baseline.py` 内部注入的 `legacy_usb_extcon` /
`legacy_board_thermal_zone` 也搬进了仓库这份 init，否则 `make-618-image.sh --set init`
又会把电源兼容参数洗掉。

判断依据不要用「文件看起来差不多」：恢复后的两份文件用 `repack-ramdisk.py` 重打包，
再从镜像里抽出来和线上镜像逐字节比较，`etc/module-order`（838 B）和 `init`
（35335 B）都完全一致。

## 4. 6.18 运行时

### 4.1 `mobile-data` 的 300 秒 last-resort reboot

5.4 rootfs 的 `changxing60-post` 会启动 `cellwatch`（`mobile-data watch`）。6.18 没有
modem，约 300 秒后它判定 WAN 不可用，执行 last-resort reboot——表现是“进 Linux 几分钟
自己重启”，很容易误判成崩溃/看门狗。

修法：`/etc/init.d/changxing60-post` 的 `start_service()` 开头加 `uname -r` 的 `6.*`
guard，跳过整套 vendor modem/WiFi watcher。仓库 overlay 已同步；现场 rootfs 也已改。

### 4.2 5.4 状态页 daemon

见 1.3：`changxing60-screen` 会把背光写 0%，6.18 上禁用。

### 4.3 听筒：AW87xxx 的 Receiver 模式（不是 codec EAR）

之前按 codec EAR 测（`tools/audio/receiver-playback.sh`）：`aplay` 跑完但
`EAR Switch event failed: -110`（`rcv dvld`），没声音；AW87xxx 写 `Receiver` 又报
`profile_cfg not load`。

ACF 正常加载后（`acf parse success`，profile 有 `Music`/`Voice`/`Receiver`），改用
`tools/audio/receiver-amp-playback.sh` 走 AW87xxx 的 `Receiver` 模式：

- AW 日志 `aw87xxx_dev_check_reg_is_rec_mode: reg status is receiver mode`、
  `is_rec_mode:1`；
- ACF 的 `Receiver` profile 正常加载；
- FAST `hw:0,3` 播 4 秒测试音，**听筒有声**。

结论：这块板的听筒是 AW87xxx 的 `Receiver` 模式，和扬声器的 `Music` 是两个 profile；
不是 codec 的 EAR DVLD 路径。`Ext Ear Switch` 这个控件不存在，脚本里跳过即可。
两个脚本都放进了 rootfs `/usr/share/changxing60/`（overlay 同步）。

### 4.4 扬声器再次无声：`fast-playback.sh` 不在 rootfs 里

现象：之前扬声器正常，后来 `aplay` 能完整跑完但没声音；dmesg 里 ACF 加载成功、
AW87xxx probe 成功，profile 文件也有 `Music`/`Voice`/`Receiver`。

原因：`fast-playback.sh` 负责把 AW87xxx 切到 `Music` 并设置 FAST/IIS0/AO 路由。镜像里
只有 initramfs 的 `/usr/share/changxing60/fast-playback.sh`；`switch_root` 后 rootfs 的
`/usr/share` 把它盖住，rootfs 里没有同名脚本，于是 amp 停在默认 `Off`，单独 `aplay`
不会开功放，听起来就是“又没声音”。

修法：把脚本放进 rootfs（`openwrt/overlay/usr/share/changxing60/fast-playback.sh`），
现场直接 `scp` 到 `/usr/share/changxing60/` 也行；`boot/make-618-image.sh` 的
initramfs 拷贝只对 `switch_root` 前有效，不能替代 rootfs 里的那一份。测试：

```sh
sh /usr/share/changxing60/fast-playback.sh /usr/share/changxing60/speaker-test.wav 3
```

用 48 kHz/16-bit 立体声 1 kHz WAV，2–3 秒即可；脚本会设置 FAST card0 pcm3、
profile `0x404b0000`、IIS0 路由和 amp `Music`，结束后恢复原 profile 并关掉
`agdsp_access_en`。

### 4.5 四个 SoC 温控一直 deferred：nvmem provider 没绑定

现象：`devices_deferred` 里长期有 `64270000/64280000/64290000/642a0000.thermal`，
拿不到任何板级温度。

原因是链条断在最上游，不是时钟也不是设备树：

- DT 里四个 thermal 节点（`sprd,thermal_r5p0`）都有
  `nvmem-cells = <&thmN_ratio>`，probe 第一件事就是
  `sprd_thm_cal_read("thm_ratio_cal")` → `of_nvmem_cell_get()`。
- 这些 cell 的 provider 是 `efuse@160000`，compatible 为
  **`sprd,qogirn6pro-efuse`**（`work/stock.dtb` 实测）。
- 移植的驱动 `drivers/nvmem/sprd-efuse.c` 只匹配 `sprd,ums312-efuse` 和
  `sprd,qogirn6lite-efuse`。provider 从未注册 → cell 查询永远返回
  `-EPROBE_DEFER` → 四个 thermal 永远 deferred。

**不要被 `ls /sys/bus/platform/drivers` 骗了**：`boot/init` 的 `pdrv` 列的是
*已注册的驱动*，`sprd-efuse` 出现在那里只证明驱动编进去了。而没有驱动的设备
不会进 `devices_deferred`，所以「efuse 不在 deferred 列表里」恰恰是它没绑上的证据。

修法：`kernel/patches/nvmem-sprd-efuse-qogirn6pro.patch` 增加
`qogirn6pro_data {blk_nums=51, blk_offset=53, blk_double=true}` 和对应 compatible。
几何值是 Unisoc 5.15 树的值，并用 DT 自洽校验过：efuse cell 最大偏移 200..203，
51×4=204 字节刚好覆盖。`prepare-kernel.py` 里本来就带这段（新树重跑会用上），
但当前编译树是更早打的补丁，所以镜像里没有，需要单独打这个 patch。

2026-10-30 上机确认：`#67`（`boot-thermal-618-v2.img`）四个控制器全部绑上
`sprd-thermal-r5p0`，`devices_deferred` 里只剩 usb，`/sys/class/thermal`
从 5 个变成 24 个 zone（19 SoC + chg/nr/pa/board + battery），温度 36–49 ℃。
仍需注意 `64400000.spi:pmic@0:adc@504` 会在早期打一条
`calib err! big_scale_calib1:-517`，`-517` 就是 `-EPROBE_DEFER`
（efuse provider 还没绑），重试后正常绑定，别把这个当成新 bug。

### 4.6 `flash-linux-checked.py` 的 misc 门禁要按 BCB 窗口比对，不能整分区比对

原来第 16 行是 `assert before == misc-restored.img`。但每次成功启动，bootloader
都会改写 2048..2079 这 32 字节 BCB（`slot_suffix`、success/retry 位、CRC32），
所以整分区比对在**第二次**刷机时必然失败——2026-10-30 那次就是在这里中止的
（实测只差 7 字节，全部落在 2049..2079，窗口外 0 字节不同）。

改成：长度必须仍是 1 MiB，且 `[0,2048)` 与 `[2080,)` 与
`misc-restored.img` 逐字节相同；2048..2079 交给后面的
`after[:2048]==before[:2048] and after[2080:]==before[2080:]` 和
`after[2048:2080]==bcb` 两道断言继续守住。**真正的安全属性（窗口外一个字节都不许动）
没有被放松**，放松的只是「BCB 必须有特定内容」这条本来就不成立的假设。

### 4.7 重编内核前必须先把 Docker 树和「已验证镜像的源码快照」对齐

`#66` 第一次上机时 `stage=modules-done loaded=42 failed=1`：

```
sprd-dmaengine-pcm.ko: Unknown symbol ums9620_audcpglb_gate_read (err -2)
```

符号由 `drivers/clk/sprd/ums9620-clk.c` 末尾那段 7552n 诊断代码
（`EXPORT_SYMBOL_GPL(ums9620_audcpglb_gate_read)`）提供，而这个文件在
`/k/linux` 里是**没有这段的旧版本**（mtime 10-29 09:20，比 overlay 还新，
但内容是干净的厂商版）。镜像里的 `.ko` 是老版本编的，于是加载失败。

教训不是「哪个文件」，而是**增量重编的内核必须与镜像里那批模块同源**。
对齐方法（54 个 overlay 文件逐个 cmp）：

```sh
docker run --rm -v changxing60-linux618:/k -v "D:/Changxing60linux:/repo" alpine sh -c '
mkdir -p /tmp/o && tar xzf /repo/baseline/wifi-verified-20261029/kernel-source-overlay.tar.gz -C /tmp/o
cd /tmp/o && for f in $(find . -type f); do cmp -s "$f" "/k/linux/$f" || echo "DIFF $f"; done'
```

期望输出**为空**。2026-10-30 实际跑出来是：

```
DIFF ./drivers/clk/sprd/ums9620-clk.c          ← 树里缺诊断段（真回归）
DIFF ./drivers/cpufreq/sprd-cpufreq-v2-driver.c ← 树里多两个 sysfs 属性（未随镜像验证过）
DIFF ./drivers/power/supply/bq2560x-charger.c   ← 树里是新版，等于 power-fix 的 source-after，属正常
```

前两个按 overlay 还原，第三个保留（它是 power-charge 镜像之后的合法改动）。
还原后重编，`loaded=43 failed=0` 恢复。

因为 `.config` 每次都用 `allnoconfig` + `merge_config` 重生成，配置不会保留上次
的手动改动；**配置不是问题来源，源码才是**。
