## 一、为什么换 6.18

在厂商 5.4 上折腾了很久，音频始终不出声。逐条排除后确认：

| 排除项 | 依据 |
|---|---|
| 寄存器位定义错 | 和 `sprd-linux-devs/linux` 的 `sound/soc/sprd/unisoc/include/` 逐行对比，**完全一致** |
| 设备树用错 | 用的是 `Spreadtrum UMS9620 SoC` 厂商 DTB，和 Android 同一份 |
| `sound-dai` 全 0 是 bug | Android 上也是全 0 |
| mixer 值不对 | 照抄 Android 通话时 326 个控件的值，无效 |

真正的断点（当时的判断）：**crossbar 开关 `S_NORMAL_AP01_P_CODEC` 控件写入成功，但对应
DAPM 控件 `Off in 1 out 0`**，路由表里两条都在、无条件、已注册、dmesg 无任何错误。

**更正（2026-10-26 晚）**：把这一段早期写成「5.4 的 DAPM 始终不动」是错的。
复核确认：**5.4 上播放和录音通路实际都被点亮过**（PCM 能进 RUNNING、DAPM 有控件上电），
只是**双向无声**。准确的描述是「通路点亮了但声音出不来」，不是「DAPM 完全不动」。
这个区别很重要 —— 意味着 5.4 上仍可能有未排查的环节，换内核不是唯一解释。

同样的驱动代码，在 `sprd-linux-devs` 的 6.18 树上音频是通的（VIPME M8 实测），
在 5.4 上不通。5.4 这套组合（厂商内核 + 厂商模块 + realme C51/C53 重编模块）**没有任何成功先例可对照**。

所以换 6.18。

## 二、最大的发现：不是设备树，是缺驱动

前三次启动全失败，pstore 一个字都没有，看起来像「早期 panic / 设备树问题」。
中途还专门做了一个最小设备树去试 —— **方向错了，白折腾两轮**。

真正的原因在读 M8 的 `prepare-kernel.py` 时发现：

**主线 `e5-6.18` 分支是给 E5（UMS9621）的。UMS9620 的支持完全靠设备层注入。**

```c
// work/m8/prepare-kernel.py
append('drivers/clk/sprd/Makefile', 'ums9620-clk.o',
       'obj-$(CONFIG_SPRD_UMS9620_CLK) += ums9620-clk.o')
append('drivers/clk/sprd/Kconfig', 'config SPRD_UMS9620_CLK',
       'config SPRD_UMS9620_CLK\n\tbool "Unisoc UMS9620 clocks"\n\tdepends on ARM64 && SPRD_COMMON_CLK')
```

主线树里 `drivers/clk/sprd/` 只有 `sprd-ums9621.c`，**没有 `ums9620-clk.c`**，
Kconfig 里也没有 `SPRD_UMS9620_CLK` 这个选项。

**没有时钟驱动 → 时钟树起不来 → 内存控制器、UART、所有外设全废 → console 都出不来。**
这完美解释了「三次启动零日志」。

### 注入的驱动

| 文件 | 作用 |
|---|---|
| `drivers/clk/sprd/ums9620-clk.c` | **时钟树**（最关键） |
| `include/dt-bindings/clock/sprd,ums9620-clk.h` | 时钟 ID 定义 |
| `include/dt-bindings/reset/sprd,ums9620-reset.h` | 复位 ID |
| `drivers/pinctrl/sprd/pinctrl-sprd-qogirn6pro.c` | 引脚控制 |
| `drivers/pmdomain/sprd/ums9620-ipa-sys.c` + `Makefile` | IPA 电源域 |
| `drivers/usb/phy/phy-sprd-ums9620-ssphy.c` | USB3 SS PHY |
| `drivers/thermal/sprd_thermal_r5p0.c` | 温度传感器 |
| `drivers/cpufreq/sprd-cpufreq-v2-driver.c` + `.h` | 调频 |
| `include/dt-bindings/soc/sprd,qogirn6pro-{mask,regs}.h` | 寄存器掩码定义 |

`prepare-kernel.py` 还会对 `ums9620-clk.c` 做 API 适配（donor 树和 6.18 的时钟核心接口不同）：
`SPRD_PLL_HW` → `SPRD_PLL_FTABLE_HW`、`SPRD_COMP_CLK_DATA_OFFSET` 插入偏移参数、
给 reset provider 加 `spin_lock_init`。

## 三、构建环境（三个坑，都踩过）

### 坑 1：clang 版本

6.18 要求 **clang ≥ 15**。原来的构建容器是 Ubuntu 20.04 + clang 12，直接报
`Sorry, this C compiler is not supported`。GCC 9.4 也编不过（vDSO 的 `sigreturn.S` 报
`__NR_rt_sigreturn` 未定义）。

**解决**：`kernel/Dockerfile.618` —— Ubuntu 24.04 + clang-18 / lld-18 / llvm-18。

```dockerfile
FROM ubuntu:24.04
RUN apt-get install -y clang-18 lld-18 llvm-18 gcc-aarch64-linux-gnu \
    bc bison flex libssl-dev libelf-dev libdw-dev cpio xz-utils python3 git make
# 建无版本号的工具别名（kernel 构建脚本要用 llvm-objcopy 等）
for t in clang ld.lld llvm-ar llvm-nm llvm-objcopy llvm-objdump llvm-readelf llvm-strip; do
    update-alternatives --install /usr/bin/$t $t /usr/bin/$t-18 100
done
```

### 坑 2：符号链接被 Windows 吃掉（最隐蔽的一个）

在 Windows 文件系统上 `git clone`，`core.symlinks` 默认关闭，
**符号链接会被写成「内容是目标路径的普通文本文件」**。

具体表现：`arch/arm64/tools/syscall_64.tbl` 本应是指向 `../../../scripts/syscall.tbl` 的链接
（17KB 的 syscall 表），结果变成 28 字节的文本文件，内容是那个路径字符串。

后果：syscall 表生成器读出空表 → `generated/uapi/asm/unistd_64.h` 里
**只有 `#define __NR_syscalls 1`，一个真实 syscall 都没有** →
vDSO 编译报 `__NR_rt_sigreturn used as an immediate value` 未定义 → 编译失败。

这个错误看起来像编译器问题，实际是文件系统问题。

**解决**：内核树放在 **Docker 卷**（Linux 原生文件系统）里，不在 Windows 目录。

```bash
docker volume create changxing60-linux618
docker run --rm -v changxing60-linux618:/k changxing60-kbuild-618 \
  sh -c 'git clone --depth 1 --branch e5-6.18 -c core.symlinks=true \
         https://github.com/sprd-linux-devs/linux.git /k/linux'
```

### 坑 3：CRLF

Windows 上 checkout 的文件带 CRLF，Kconfig 解析器直接语法错：
```
Documentation/Kconfig:24: syntax error
Documentation/Kconfig:24:warning: ignoring unsupported character ''
```
用 Docker 卷就没有这个问题。

## 五、打包与刷机

### 为什么需要 wrap-image.py

LK 把内核固定载入 `0x80080000`，但 5.8+ 的内核 `text_offset = 0`，要求 2MiB 对齐。
`upstream/wrap-image.py` 加一个跳转桩，让真正的 Image 从 `0x80200000` 开始跑。

```
work/kout/Image.lk: stub 0x180000 + Image 0x1960808
```

### boot 镜像是 v4 格式

`work/boot-linux-slotb.published.img` 是 Android boot image **v4**（`ANDROID!` + hdr_ver=4）。
`boot/swap-kernel.py` 的布局：

```
[header 4096] [kernel 对齐 4096] [ramdisk 对齐 4096] [AVB blob] [padding] [footer 64]
```

只替换 kernel、更新 header 的 `kernel_size`、更新 footer 的 `original_size`；
ramdisk 和 AVB blob 原样保留（设备有 boot 校验绕过）。

### 刷机

**不要手写 `dd`。** 2026-10-28 曾按上面这种裸 `dd` 片段写 misc，把整块分区的
bootloader control 区域写坏，设备要拆机才救回来。现在只有两个脚本允许碰这两个分区：

| 场景 | 做法 |
|---|---|
| Linux 里换 `boot_b` 镜像 | `baseline/wifi-resume-20261028/flash-linux-checked.py <img>` |
| Android 里切到 Linux（`boot_b` 已是目标镜像） | 装 `tools/bootlinux-app`：它只读当前 misc、校验 CRC、派生 32 字节试启动记录，不碰 `boot_b` |
| Android 里换 `boot_b` 镜像 | **目前没有审计过的脚本**，先别做；要么在 Linux 里换，要么把整个流程补成脚本再动 |

> `baseline/wifi-resume-20261028/` 下的 `flash-android-checked.py` 是历史脚本：
> 镜像路径和设备串号都写死在里面，只对当时那一轮有效，不要当通用工具用。

两者都是同一套约束：镜像必须是 64 MiB 且以 `ANDROID!` 开头、哈希与同名 `.json` 一致；
`boot_b` / `misc` 按 `PARTNAME` 唯一定位（UFS 的 LUN 编号每次启动会变，Linux 里没有
`/dev/block/by-name`）；**misc 只写偏移 2048 起的 32 字节** `bootloader_control`，
写完回读比对，并确认 2048 之外一个字节都没变；任何一步不符就停止，且不自动重启。
Android 侧脚本还会先核对设备当前 misc 与这份原厂备份是否逐字节相同。

只写 `boot_b` 和 `misc` 的那 32 字节，`boot_a`（Android）永不触碰，GPT 不动。
启动失败时引导器自动回退 Android。

**从 Linux 回 Android 的方法**：`changxing60-next-boot android` 后重启（LuCI 的
"启动目标"面板是同一动作的封装）。`echo c > /proc/sysrq-trigger` 也能让它落回
Android，但那是"烧掉一次 slot B 的 tries"的路径，`panic_on_oops=1` 时一次 Oops
就能触发 —— 能用命令就别用 panic。

### 上文那些"卡住点"后来怎么解的

- **声卡注册 -517**：链路 0 是 `FE_ST_NORMAL_AP01`，它引用的 provider 不在手机音频
  构建里。按本机实际链路逐条跳过，而不是照抄 M8 的链路名；`agdsp_pd` 继续用内存内
  改 DTB 的办法把 `agdsp-access` 变成 power-domain provider。见 `67c7d6b`、`ce214b6`。
- **UFS 崩溃**：不是补个空指针保护就完事，而是补齐 `sprd,ufshc` 匹配、reset 名对齐，
  以及 `ufs_eb / ufs_cfg_eb / ufs_hclk` 三个门控和 `ufs_hclk` 的父时钟。
  见 `7efc0d7`、`29fd6a2`、`6f6d49e`。
- **内屏**：三层根因（panel 参数、SDIO 电源时序、未 strip 的 `sprd-drm.ko`）逐个拆除，
  见 `4cf11fd`。
- **Wi-Fi 固件断言 `cmd_tx.c:2374`**：根因不在命令序列。移植版按 **AB 芯片 revision**
  强选 XPE INI，原厂按 **IPD eFuse** 选择；本机 IPD=0，应当用普通
  `wifi_board_config.ini`。改正后双频正常，并补齐了 3 MiB 固件容器按 IPD 选 XPE
  分段的逻辑。详见 [`WIFI-STATUS-2026-10-29.md`](WIFI-STATUS-2026-10-29.md)。
- **外设各自 probe 失败**：`sdhci_sprd_set_power()` 必须走 `sdhci_set_power_noreg()`、
  `CONFIG_SDIOHAL` 必须关、模块必须 strip。见
  [`PITFALLS-2026-10-28.md`](PITFALLS-2026-10-28.md)。

### 以下两节是历史，故障均已修复

保留原文只为记录当时的判断过程。

#### （历史）音频：模块能载，声卡注册不上

`work/m8/audio.py` 的两个补丁已应用：

1. **`audio-legacy-dt.c`**（注入到 `drivers/unisoc_platform/sprd_audio/`）
   把厂商 DTB 里的 `agdsp-access` 节点在**内存里**改造成 power-domain provider
   （`compatible` → `sprd,agdsp-pd`，加 `#power-domain-cells = <0>`），
   再给 9 个音频消费者节点（`unisoc,qogirn6pro-vbc`、`unisoc,ump9620-audio-codec` 等）
   加上 `power-domains` 引用。新驱动用 runtime-PM，老的 `agdsp_access()` 已经没了。

2. **卡片驱动补丁**：`sprd_card_link_enabled()` 跳过 `AGCP_IIS0_TX` 和
   `DisplayPort MultiMedia` 两条链路（它们的 AGCP IIS provider 不在手机音频构建里）。

模块加载顺序和结果：

```
agdsp_pd ✓
snd-soc-sprd-codec-ump9620-power ✓
snd-soc-sprd-codec-ump9620 ✓
snd-soc-sprd-vbc-v4 ✓
snd-soc-sprd-vbc-fe ✓
snd-soc-sprd-pa-aw87xxx ✓
sprd-platform-pcm-routing ✓
snd-soc-sprd-card ✓（加载成功但没注册声卡）
```

失败点：

```
vbc-rxpx-codec-sc27xx sound@0: asoc_sprd_card_parse_of: Parsing dai link 0 failed(-517)!
vbc-rxpx-codec-sc27xx sound@0: asoc_sprd_card_dai_link_of: xx_dai_name is NULL
vbc-rxpx-codec-sc27xx sound@0: asoc_sprd_card_parse_of: Parsing dai link 18 failed(-517)!
```

`-517` = `-EPROBE_DEFER`，来自 `snd_soc_of_get_dai_name()` —— 链路引用的组件 DAI 没注册。
dai link 0 是 `FE_ST_NORMAL_AP01`。

M8 的补丁只按名字跳过两条链路，**我们这台机器的链路结构和名字跟他们不同**，
需要逐条适配。

#### （历史）UFS（rootfs / 界面的前提）：三轮修复未完成

这台机器的存储是 **UFS**（5.4 上块设备是 `/dev/sda`，不是 `mmcblk`），
rootfs 在 UFS 上，UFS 不通就没有 `switch_root`、没有界面。

6.18 的 `drivers/ufs/host/ufs-sprd.c` 修了三轮：

| 轮 | 问题 | 处理 | 结果 |
|---|---|---|---|
| 1 | DT `compatible = "sprd,ufshc"`，驱动要 `sprd,ums9620-ufs` | 驱动加一项匹配 | probe 进去了 |
| 2 | DT reset 名 `ufs_soft_rst`/`ufsdev_soft_rst`，驱动要 `controller`/`device` | 改成 DT 的名字 | `ufs device reset!` 通过 |
| 3 | 驱动要 `sprd,ufs-anlg-syscon`/`sprd,aon-apb-syscon`，DT 没有 → NULL 解引用 | 加空指针保护 | 崩在 `sprd_ufs_n6_hce_enable_notify+0x68` |

第 3 轮的崩溃点在 `ufs_sprd_n6_host_reset()` 的 `reset_control_assert()`。

**当时已把 `sprd,ufshc` 匹配项撤掉**，让 UFS 不 probe，避免崩溃阻塞其他测试。
这一撤除后来已恢复：UFS 目前正常工作，根文件系统就在它上面（见本章开头的状态表）。

## 八、教训

1. **别急着怀疑设备树。** 三次失败都像 DTB 问题，实际是缺驱动。
   读别人的设备层脚本（`prepare-kernel.py`）比猜快得多。
2. **工具链版本要查清楚。** clang 12 → 18 是硬门槛，GCC 也编不动 vDSO。
3. **Windows 上不要直接 clone 内核树。** 符号链接会被转成文本，症状诡异（像编译器 bug）。
4. **端口探测不可靠。** 启动过程中内核网络栈会短暂接受 TCP 连接，
   `/dev/tcp` 报「开」但实际没有服务。要连上去验证协议。
5. **pstore 是没串口时的眼睛**，但**「没有 pstore」不能单独证明早期 panic**。
   只要内核走到 ramoops 初始化之后，panic 就能被捕获，重启后从 Android 的
   `/sys/fs/pstore/` 读出来。反过来，「pstore 里没有新内容」也可能意味着：
   panic 在 ramoops 之前、ramoops 驱动没绑上、或那次启动根本没走到写 pstore 的地方。
   我们三次失败最初据此判断「早期 panic」，后来证明真正的短板是**内核里根本没有时钟驱动**
   —— 现象一致，但结论是猜的。要区分只能靠串口或更早的日志手段。
6. **别整分区写 misc。** 整分区备份存在不代表可以随意写：只写偏移 2048 的 32 字节，
   写前核对、写后回读、只允许 2048..2079 变化。见 `misc:` 那次提交。
7. **`panic_on_oops=1` 会让调试变成赌博。** 一次 Oops 就是一次重启，而每次失败启动都会
   消耗 slot B 的 tries（两次失败就自动回退 Android）。调试期内不要在真机上靠 panic 验证。
8. **仓库不等于构建树。** 改完源码要同时更新 `baseline/*/kernel-source-overlay.tar.gz`，
   否则下次照着仓库重编会得到另一套行为。
